# 2026-04-12 학회 간사님 오케스트레이션 하네스 설계안

## 1. 목적

이 문서는 `간사님` 에이전트를 실제로 굴리기 위한 `오케스트레이션`과 `하네스`를 설계한다.
여기서 오케스트레이션은 `어떤 요청을 어떤 스킬 순서로 처리할지 결정하는 규칙`이고, 하네스는 `그 규칙을 실행하고 상태와 로그를 관리하는 런타임 계층`이다.

즉, 지금까지 만든 시스템 프롬프트와 `SKILL.md`가 `업무 지식`이라면, 이 문서는 그 지식을 실제로 연결하고 운영하는 `실행 구조`를 정의한다.

---

## 2. 한 줄 정의

`간사님 하네스`는 사용자의 요청을 분류하고, 적절한 스킬을 순차 또는 연쇄 실행하고, 사람 승인 구간을 멈춰 세우고, 변경 이력과 결과물을 남기는 운영 실행 계층이다.

---

## 3. 범위

하네스는 아래를 담당한다.

- 요청 유형 분류
- 스킬 선택
- 스킬 간 순서 제어
- 승인 필요 단계에서 일시 정지
- 상태 저장
- 변경 이력 기록
- 결과물 저장 위치 관리
- 예외 케이스 분리

하네스가 직접 하지 않는 일은 아래와 같다.

- 회원구분 규칙 자체 판단
- 회비 기준표 해석의 세부 로직
- 문안 작성의 실제 내용 생성
- 공식 메일 최종 발송 결정
- 환불, 송금, 자격 박탈 같은 확정 행위

즉, 하네스는 `무엇을 할지 정하고 연결하는 층`이지, 각 업무의 세부 판단을 대신하는 층은 아니다.

---

## 4. 상위 구조

추천 구조는 아래 6개 계층으로 나눈다.

### 4-1. Intake

사용자 요청, 업로드 파일, 메일 아카이브, 스프레드시트 링크, 드라이브 폴더 같은 입력을 받는다.

### 4-2. Router

요청을 읽고 어떤 스킬이 필요한지 1차 분류한다.

### 4-3. Planner

단일 스킬로 끝나는지, 여러 스킬을 순차 실행해야 하는지 계획한다.

### 4-4. Runner

실제 스킬을 호출하고 결과를 수집한다.

### 4-5. Approval Gate

사람 승인 필요 상태를 만나면 자동으로 멈추고 검토 큐로 보낸다.

### 4-6. Logger / State Store

작업 상태, 변경 이력, 결과물 경로, 레드플래그를 기록한다.

---

## 5. 권장 컴포넌트

하네스는 최소 아래 8개 컴포넌트로 설계하는 것이 좋다.

### 5-1. Request Classifier

요청을 아래 유형으로 분류한다.

- `dues_reconciliation`
- `membership_update`
- `protocol_reconstruction`
- `meeting_minutes`
- `notice_draft`
- `email_draft`
- `multi_step_admin`
- `unknown`

### 5-2. Skill Router

분류 결과를 스킬에 매핑한다.

- `dues_reconciliation -> society-secretary-dues`
- `membership_update -> society-secretary-membership`
- `protocol_reconstruction -> society-secretary-protocol`
- `meeting_minutes`, `notice_draft`, `email_draft -> society-secretary-meeting-comms`
- `multi_step_admin -> planner가 추가 분해`

### 5-3. Workflow Planner

복합 요청을 단계로 쪼갠다.

예시:

- 회비 파일 정리 후 명단 반영: `dues -> membership`
- 작년 메일 분석 후 공지 초안 생성: `protocol -> meeting-comms`
- 행사 등록표 정리 후 안내 메일 생성: `membership or dues-like normalization -> meeting-comms`

### 5-4. State Manager

각 작업의 상태를 아래처럼 관리한다.

- `received`
- `classified`
- `planned`
- `running`
- `waiting_for_review`
- `waiting_for_approval`
- `completed`
- `failed`

### 5-5. Approval Gate

스킬 결과에 `사람 승인 필요` 항목이 있으면 자동으로 멈춘다.

멈출 때 함께 남겨야 하는 것:

- 승인 필요 사유
- 승인권자 후보
- 관련 파일 경로
- 요약 결과
- 다음 액션

### 5-6. Change Logger

수정이 발생한 경우 아래를 반드시 기록한다.

- 작업 ID
- 파일 또는 시트 이름
- 수정 시각
- 수정 대상 항목
- 수정 전 값
- 수정 후 값
- 수정 근거
- 실행한 스킬 이름

### 5-7. Artifact Manager

결과물을 어디에 저장할지 관리한다.

- 회비 정산 결과표
- 회원 명단 업데이트안
- 운영 프로토콜 초안
- 회의록 초안
- 공지문 초안
- 승인 대기 문서

### 5-8. Review Queue

`검토 필요` 항목을 따로 모아 사람이 한 번에 볼 수 있게 한다.

---

## 6. 스킬 오케스트레이션 규칙

### 6-1. 단일 스킬 요청

아래는 단일 스킬로 끝나는 경우다.

- "이 회비 내역 정리해줘" -> `society-secretary-dues`
- "회원 명단 업데이트해줘" -> `society-secretary-membership`
- "작년 메일 읽고 프로토콜 만들어줘" -> `society-secretary-protocol`
- "회의록 초안 써줘" -> `society-secretary-meeting-comms`

### 6-2. 연쇄 실행 요청

아래는 2단계 이상으로 연결되는 경우다.

#### 회비 -> 회원명단

1. `society-secretary-dues`
2. 자동 반영 가능 거래만 추출
3. `society-secretary-membership`
4. 회원 상태 반영안 생성
5. 승인 필요시 대기

#### 프로토콜 -> 공지/회의문안

1. `society-secretary-protocol`
2. 운영 절차와 일정 구조 추출
3. `society-secretary-meeting-comms`
4. 공지문, 리마인드, 보고 메일 초안 생성

### 6-3. 중단 규칙

아래 조건이면 다음 스킬로 넘기지 않는다.

- 기준표 누락
- 대조 결과 불명확
- 승인 필요 항목 미해결
- 입력 파일 누락
- 현재 단계가 `failed`

즉, `dues` 단계에서 거래가 정리되지 않았는데 `membership`으로 넘겨서는 안 된다.

## 7. 라우팅 매트릭스

| 요청 유형 | 1차 스킬 | 후속 스킬 | 중단 조건 |
| --- | --- | --- | --- |
| 회비 정산 | dues | membership | 기준표 없음, 거래 충돌 |
| 회원 명단 정리 | membership | 없음 | 중복 후보 다수 |
| 운영 프로토콜 복원 | protocol | meeting-comms | 근거 부족, 연도 충돌 |
| 회의록 작성 | meeting-comms | 없음 | 결정사항 불명확 |
| 공지/메일 작성 | meeting-comms | 없음 | 승인권자 불명확 |
| 이메일 아카이브 기반 운영 문안 | protocol | meeting-comms | SOP 미확정 |

## 8. 상태 머신

작업은 아래 상태를 가진다.

### 8-1. 상태 정의

- `received`: 요청 접수 완료
- `classified`: 요청 유형 분류 완료
- `planned`: 실행 계획 수립 완료
- `running`: 스킬 실행 중
- `waiting_for_review`: 검토 필요 항목으로 보류
- `waiting_for_approval`: 승인 필요 항목으로 보류
- `completed`: 최종 결과물 생성 완료
- `failed`: 실행 실패

### 8-2. 전이 규칙

- `received -> classified`
- `classified -> planned`
- `planned -> running`
- `running -> waiting_for_review`
- `running -> waiting_for_approval`
- `running -> completed`
- `running -> failed`
- `waiting_for_review -> running`
- `waiting_for_approval -> running`

### 8-3. 승인 후 재개

승인 후에는 전체 작업을 처음부터 다시 하지 않고, `마지막 성공 단계 다음`부터 재개하는 것이 좋다.

예시:

- `dues` 성공
- `membership`에서 승인 대기
- 승인 후 `membership`부터 재실행

## 10. 결과물 저장 규칙

하네스는 결과물을 한 폴더에 몰아넣지 말고 `job_id` 기준으로 저장하는 편이 좋다.

권장 구조:

```text
runtime/
  jobs/
    job-2026-04-12-001/
      intake.json
      plan.json
      state.json
      logs/
        events.jsonl
        changes.jsonl
      artifacts/
        dues_reconciled.xlsx
        membership_update_proposal.xlsx
        notice_draft.md
      review/
        review_items.md
      approval/
        approval_items.md
```

이 구조의 장점은 아래와 같다.

- 작업 단위로 결과 추적 가능
- 승인 대기 중단점 관리 가능
- 나중에 감사 로그로 사용 가능
- 특정 결과물만 재생성 가능

## 11. 로그 설계

로그는 최소 두 종류가 필요하다.

### 11-1. 이벤트 로그

작업 흐름 자체를 남긴다.

예시:

- job received
- classified as dues_reconciliation
- routed to society-secretary-dues
- waiting_for_review
- resumed after review
- completed

### 11-2. 변경 로그

실제 데이터 수정 내용을 남긴다.

예시 필드:

- timestamp
- job_id
- skill
- target_file
- target_row_or_field
- before_value
- after_value
- reason
- source_reference

---

## 12. 승인 게이트 설계

승인 게이트는 단순한 yes/no 버튼이 아니라, `무엇을 승인하는지`가 보여야 한다.

승인 카드에 최소 포함할 항목:

- 작업 요약
- 승인 필요 사유
- 영향 범위
- 관련 파일
- 추천 액션
- 승인 시 다음 단계
- 반려 시 다음 단계

승인 게이트는 아래 두 상황에서 특히 중요하다.

- 회원 상태가 바뀌는 경우
- 외부 발신 문서가 나가는 경우

---

## 13. 실패 복구 전략

하네스는 한 단계 실패가 전체 붕괴로 이어지지 않게 설계해야 한다.

### 13-1. 실패 유형

- 입력 파일 읽기 실패
- 기준표 누락
- 스킬 결과 불완전
- 승인 정보 누락
- 저장 실패

### 13-2. 복구 원칙

- 마지막 성공 단계는 유지
- 실패 단계만 재실행
- 변경 로그는 롤백이 아니라 `실패 기록`으로 남김
- 검토 필요 큐로 보내고 강제 진행하지 않음

## 14. MVP 하네스

처음부터 복잡하게 만들 필요는 없다. 최소 하네스는 아래 5개만 있어도 된다.

1. 요청 분류기
2. 스킬 선택기
3. 상태 파일 `state.json`
4. 승인 대기 큐
5. 변경 로그 `changes.jsonl`

MVP에서도 꼭 필요한 규칙은 아래다.

- `dues -> membership` 연쇄만 지원
- `protocol -> meeting-comms` 연쇄만 지원
- 승인 필요 상태에서 자동 중단
- 결과물 경로 저장

---

## 15. 확장형 하네스

운영이 안정화되면 아래를 추가한다.

- 우선순위 큐
- 병렬 실행 제한
- 사용자/위원회별 권한 분리
- 캘린더 이벤트 자동 생성
- 메일 초안 자동 적재
- 반복 일정 기반 예약 작업
- 대시보드

## 18. 핵심 판단

이 설계에서 가장 중요한 것은 `스킬을 많이 만드는 것`이 아니라, `언제 멈추고 누구에게 넘길지`를 명확히 하는 것이다.

좋은 하네스는 많이 자동화하는 하네스가 아니라,

- 잘 분류하고
- 예외를 숨기지 않고
- 승인 필요 구간에서 멈추고
- 로그를 남기고
- 다음 단계를 명확히 제시하는 하네스다.
